# Task 9: atomic sale mutation replay

Each sale mutation now records a canonical SHA-256 fingerprint on its sale document or tombstone and creates a scope-scoped mutation identity document in the same Cosmos batch as the sale write, inventory guard update, and metadata CAS. The fingerprint covers operation, scope, lot, sale, the original base version (including omitted versus explicit zero), and payload with object keys sorted recursively. Mutation IDs are hashed for safe identity-document IDs.

After acquiring the inventory guard, the repository checks the identity document before reading the active lot generation or validating stock. An exact retry returns the sale only while its committed version and fingerprint are still current. Reused IDs with changed requests, retries after a later sale mutation, and retries pointed at another lot return 409. When `baseVersion` is omitted, version validation treats it as zero, so it supports a new sale while existing sale updates and deletes require the current explicit version. The HTTP handler preserves the omitted value for this repository rule.

Stock validation uses `loadCoherentSyncSnapshotInputs`, which reads only the active preset generation and verifies the metadata pointer afterward. Raw whole-snapshot documents are not inventory sources. Legacy unversioned preset documents continue supplying embedded sales unless metadata selects entity mode. Metadata churn becomes a sale version conflict (HTTP 409). The regressions also cover duplicate concurrent writes, lost upsert/delete responses, changed payload/operation/base version, historical replay after later edits, orphan raw lots and sales, legacy preset sales, and historical oversold inventory edits.

The mutation identity record is retained indefinitely so a later request cannot reuse an old ID after the sale document changes. This adds one small Cosmos document per unique sale mutation; no cleanup policy is included in this task.
